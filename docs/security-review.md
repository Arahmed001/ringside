# Pre-launch security review

Round 126, 2026-10-06. A read of the whole application (every API route, the account and forum libraries, the importers and the fetcher, the headers, the public API, the error paths, the dependencies) looking for what is really wrong before real visitors arrive, with a fix and a regression test for each real finding. Things that are a decision for the operator, or that could not be shown to be wrong, are listed under "Left" and were not changed. `docs/security.md` (headers and policy) and `docs/accounts.md` (account protections) describe the standing design; this file is what this review found.

Not touched on purpose: `scripts/vendor-*.ts` and the vendor load and fetch tooling (reported only; nothing to report).

## Found and fixed

| # | Finding | Where | Fix | Test |
|---|---|---|---|---|
| 1 | **An unauthenticated request could make the server buffer a body of any size.** The 16 KB limit was checked after `req.text()` had read the whole body into memory, and counted characters, not bytes. Every mutating route, including sign-in and sign-up, goes through it. | `lib/accounts/api.ts:30-60` (`postBody`) | The body is read as a stream and cancelled the moment it passes 16 KB of bytes; a declared `Content-Length` over the cap is refused before the body is touched. | `tests/security-review.test.ts`, "a request body is cut off at the cap" (stream of 50 MB is cancelled after about 17 KB; declared length; bytes not characters; an ordinary body still passes) |
| 2 | **A username typed into the sign-in form could spend another limiter's allowance.** The sign-in limiter was keyed by the bare name, the same table that holds `pw:<user id>` (change password), `del:<user id>` (delete account) and `reset:<name>`. Six sign-in attempts for the "username" `pw:7` locked user 7 out of changing their password for 15 minutes (likewise `del:7`, `reset:alice`), from any address. | `app/api/account/login/route.ts:9-16`; keys used at `app/api/account/password/route.ts:10`, `delete/route.ts:11`, `reset/route.ts:11` | The sign-in key is `login:<name>`, a prefix no other key can start with. | "a typed username cannot spend another limiter's allowance" |
| 3 | **The daily limit on reports and proposals could be reset at will.** A refused submission "forgave" the allowance by clearing the whole window, which also forgave every accepted one: an account could send ten valid reports, one invalid one, and have ten more, indefinitely (the queue an editor must read is the cost). | `app/api/report/route.ts:25,36-37`; `app/api/contribute/route.ts:19,26-27` | The allowance is only checked up front (`left`) and spent (`take`) when the submission is accepted. A refused one still costs nothing, which `tests/reports.test.ts` already holds. | "a refused report or proposal does not forgive the ones already accepted today" |

All three tests fail on the code as it was (verified by reverting the fix) and pass now.

## What was checked, and found sound

- **Sign-up, sign-in, sessions, cookies.** scrypt (N=2^15, r=8) with a random salt per user and the cost in the string, so it can be raised; `timingSafeEqual`; a dummy hash so an unknown name costs the same as a wrong password; passwords checked for length by characters, a short common list, the username, one repeated character. Session tokens are 32 random bytes, only their SHA-256 is stored, the session is replaced on sign-in, on password change and on reset (every other device signed out), expiry is checked on every request, a disabled account is signed out. The cookie is `HttpOnly; SameSite=Lax`, `Secure` over https (`SITE_URL` or `X-Forwarded-Proto`), no value read from the visitor goes into it (`lib/accounts/api.ts:24-27`, `lib/accounts/users.ts`). Deleting an account needs the password again and scrubs the name from the activity log.
- **CSRF.** Every mutating handler (POST and DELETE: sign-up, sign-in, sign-out, password, reset, delete, settings, sessions, standing, picks, watchlist and both imports, contribute, report, the review and source-check routes, the forum) starts with `postBody`, which refuses an `Origin` that is not this site (`sameOrigin`, `lib/accounts/guard.ts:11-23`); a request with no `Origin` and no `Sec-Fetch-Site` is not from a browser. No GET changes anything. There are no server actions (`"use server"` appears nowhere). The account GETs set no CORS headers, so another site cannot read them.
- **Rate limits.** Per address and per name for sign-in and reset, per address for sign-up, per user for writes, picks, reports (10 a day), proposals (10 a day), forum posts, threads and reports; the model calls have a per-visitor and a daily site-wide budget (`lib/ai-guard.ts`); the public API has 60 a minute per address. Password hashing has one site-wide budget on top, taken before any hashing starts.
- **Input validation.** Reports and corrections (`lib/accounts/corrections.ts:validateReport`): the kind, target, field and value are checked against whitelists and ranges, the source must be an `http(s)` address without credentials, quote and note lengths are bounded, control and bidi characters are stripped, a user has at most 20 open reports. Proposals (`lib/accounts/contributions.ts`) likewise. Picks and watchlist: integer ids, a bout must be open and the boxer must be in it, ceilings per account (5,000 picks, 100 watched), imports capped at 400 and 100 entries. `/api/ask`, `/api/search`, `/api/fighters`, `/api/picks`, `/api/watch`, the digest and the calendar: query lengths and list sizes are capped, dates and ids are parsed strictly, the language is checked against the list. Forum text: plain text only, no links or long digit strings, invisible characters removed.
- **SQL.** Every value goes through a bound parameter. The template-literal queries that remain interpolate only constants, fixed table names (`team_stints`/`weigh_ins`, `contributions`/`reports`, which are whitelisted in code), or whitelisted words: the review queue's `kind` and `status` (`corrections.ts`, whitelisted before use), a correction's `field` (stored only after `FIELDS` checked it and never `other`), the thread action in `lib/forum/posts.ts:209`. The hostile test feed contains `'); DROP TABLE boxers;--`.
- **SSRF and redirects.** The only fetch of an address a visitor typed is the reviewer's source check (`lib/accounts/source-check.ts` through `lib/research/fetcher.ts` in strict mode): only `http(s)`, private and reserved IPv4 and IPv6 ranges refused (including IPv4 carried in IPv6 and the cloud metadata range), the host resolved and every resolved address checked, a redirect followed only within the same host, at most three, each hop checked again, robots.txt fetched with the same care, the body capped at 2 MB, HTML and plain text only, the result shown to reviewers only. Importers and the media resolver fetch fixed Wikimedia and Wikidata addresses; an override for the Wikipedia address exists for tests only. There is no open redirect: the only redirect in the application is `/en/...` to `/...` on the same host, and no page takes a `next` or `returnTo` address.
- **XSS.** Stored text (reports, proposals, forum posts, usernames, fighter names and nicknames) is only ever rendered as React text. `dangerouslySetInnerHTML` appears three times: two JSON-LD blocks (`<` escaped, `lib/seo.ts:52`) and the nonce-carrying theme script with a constant body. Links built from stored addresses are shown only when they start with `http(s)://` and carry `rel="noopener noreferrer nofollow ugc"`. The Atom and calendar feeds escape their values. The hostile test feed puts script and image-handler text in names and nicknames and a test checks the pages.
- **Headers and policy.** Reviewed `lib/security.ts`, `proxy.ts`, `next.config.ts`: nonce-based policy without `unsafe-inline` or `unsafe-eval` in production, `frame-ancestors 'none'` except `/embed`, `nosniff`, referrer and permissions policies, COOP, HSTS only over https, no `X-Powered-By`. The portrait SVG route sets its own locked-down policy. Unchanged.
- **Public API (`/api/v1`, embeds).** Read-only, built from the same fields as the pages, nothing from accounts; off for a licensed feed until `PUBLIC_API=1` and the vendor confirmation are set; `limit` capped at 50; errors never carry an exception's text; CORS is `GET` only.
- **Errors and logs.** The error pages show a reference and nothing else; the server log line has the route, a short message and a few stack frames, never headers, bodies or query strings (`lib/error-log.ts`); the health route reports counts and an age only. No log line prints a key or a cookie (`lib/ai.ts`, `lib/providers`, `lib/doctor.ts` were read for it). `.env.example` has no live value (a test holds that).
- **Dependencies.** `npm audit --omit=dev`: 0 vulnerabilities. `npm audit`: 5 high, all one chain (`braces` through `eslint-config-next`), development-time linting only; the only offered fix is a downgrade to a version that does not match Next 16. Unchanged from `docs/security.md`.
- **Container.** The image runs as the unprivileged `node` user.

## Left, and why (nothing here was changed)

| # | Item | Where | Why left | What would close it |
|---|---|---|---|---|
| A | **The client address is the first `X-Forwarded-For` entry**, so a client that can set the header picks its own address: every per-address limit (sign-in, sign-up, forum, the model's per-visitor limit, the public API's 60 a minute) can be dodged by sending a new value each time. Behind a proxy that appends rather than replaces, the first entry is the client's own. The per-name, per-user and site-wide limits do not depend on it. | `lib/ai-guard.ts:72` (`clientId`), `lib/public-api-http.ts:29` (`clientKey`) | Documented (`docs/deploy.md`, `docs/accounts.md`), and the right fix depends on the proxy the owner chooses: take the entry the trusted proxy added, or a header it sets itself. Guessing wrong would put every visitor in one bucket. | Configure the proxy to overwrite `X-Forwarded-For` (not append) and keep the container's own port unpublished; or, once the proxy is chosen, read the last (or N-th from last) entry. |
| B | **The site-wide hashing budget (240 a minute) can be used up by anyone** with enough distinct addresses and names, which then refuses every sign-in and sign-up until the minute ends. It is a deliberate trade (a flood is refused instead of keeping every worker busy), but it is a cheap way to deny sign-in. | `lib/accounts/guard.ts:59`, used by the sign-in, sign-up, reset, password and delete routes | A design decision. Existing sessions are unaffected, and reading the site is unaffected. | A proxy-level rate limit in front of `/api/account/*`, or a CAPTCHA. |
| C | **A name can be locked out on purpose**: six wrong passwords for one name from any address lock it for 15 minutes. The reverse choice (no per-name limit) allows slow guessing from many addresses. | `app/api/account/login/route.ts` | Documented trade; the owner's call. | Two-factor sign-in, or a per-name limit that counts only unfamiliar addresses (needs more state). |
| D | **DNS rebinding between the reviewer's source-check lookup and the fetch** (the host is resolved, checked, then fetched by name). Only reviewers can start a check, the result is not shown to the proposer, and only the same host can be redirected to. | `lib/research/netguard.ts:42`, `lib/research/fetcher.ts` | Already stated in the code's own comment. Fixing it means pinning the connection to the resolved address, which touches the shared fetcher the research pipeline also uses. | Connect to the resolved address with the host in `Host`/SNI, or run the check from a network with no route to private ranges. |
| E | **The public API's "shared bucket" key is guessable**: a client that sends `X-Forwarded-For: unknown` is counted in the 600-a-minute shared bucket, ten times the 60 a minute an address gets. A consequence of A. | `lib/public-api-http.ts:26-29` | Not a separate hole once A is closed; harmless without a proxy (everyone shares it anyway). | Key the shared bucket on something a client cannot send, when A is fixed. |
| F | **Accounts have no second factor, no email and no CAPTCHA**; a lost password needs the operator. | `docs/accounts.md` | Stated product limits, not defects. | Product decision. |
| G | **Voting-style brigading in the forum**: four different accounts reporting a post hide it until an editor looks. New accounts wait five minutes and are limited to ten posts a day, so this takes effort, but it is possible. | `lib/forum/posts.ts:181` | A policy choice stated in the rules file. | Raise the threshold, or weigh reporters by age. |
| H | **`DELETE /api/contribute` and `DELETE /api/report` (withdrawing your own item) have no rate limit.** They only touch the caller's own rows and cost one indexed update. | `app/api/contribute/route.ts:31`, `app/api/report/route.ts:42` | No effect found. | Use the shared per-user write limiter. |
| I | **`img-src` allows any `https:` address** (for headshots from Wikimedia or a vendor CDN), so a scraped or stolen image URL could be loaded; and a Commons description link (`pageUrl`) is placed in an `href` as received from the Wikimedia API without a scheme check. Nothing a visitor can write reaches either; it rests on the API's answer. | `lib/security.ts` (`img-src`), `components/CreditedPicture.tsx:15` | Defence in depth only; the policy concession is documented. | Check `https://` before rendering the link; narrow `img-src` to the actual photo hosts once they are fixed. |
| J | **A bug that is not a security hole**: `escapeText` in the calendar writer replaces `;` with `"\;"`, which in a JavaScript string is just `;`, so semicolons in calendar text are not escaped as the format asks. Line breaks and backslashes are escaped, so nothing can be injected. | `lib/ics.ts:15` | Changes the bytes of a published feed and its expected-output tests; separate from this review. | Escape with `"\\;"` and update the calendar tests. |
| K | **Session cookie has no `__Host-` prefix**, which would stop a sibling subdomain from setting it. | `lib/accounts/api.ts:24` | The prefix requires `Secure`, so it cannot be used before https is certain; changing the name signs everyone out. | Adopt it at the first https deployment. |
| L | **A run of the application was not made**: this review is a code read plus the test suite; no scanner (ZAP or similar) was run against a running instance and no browser was used. | | | Run a scanner against a staging copy before launch. |
